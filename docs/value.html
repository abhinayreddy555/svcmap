The problem

AI agents struggle with raw codebases

Every time an agent answers a question about your services, it either reads raw source (slow, expensive, incomplete) or guesses (inaccurate). Neither scales.

Without svcmap
  • Scans 50–200 files per question — most irrelevant
  • Consumes 10–50K tokens just to read context
  • Misses logic that spans multiple files
  • Makes GitHub API calls on every query — rate limited
  • Reconstructs dependency graphs from scratch every time
  • May expose raw secrets or credentials in context
  • No awareness of which services are stale or changed
  • 15–30 second response time per question
With svcmap
  • Reads one focused Markdown doc — 2–4K tokens per question
  • Structured facts: endpoints, state machines, dependencies, runbooks
  • Cross-service dependency graph pre-built in PRODUCT.md
  • Local MCP server — no GitHub API calls at query time
  • Mermaid sequence diagrams for execution scenarios
  • Docs never include raw secrets — only descriptions
  • Staleness detection via HEAD SHA — agents know when to trust
  • Sub-second response from local knowledge base
How it works

One generation run, unlimited queries

svcmap runs once (or on each PR merge) and produces a living knowledge base your entire team and all AI agents can query indefinitely.

🔍
Crawl
Fetches all relevant files from GitHub. Priority-sorts routes → schemas → source → tests. Skips files >300KB.
⚙️
Extract
12 sequential LLM passes extract typed structured data. Large repos use map-reduce chunking — never truncated.
📄
Generate
12 Markdown documents per service with Mermaid diagrams, tables, and cross-references. 20K token budget each.
🗺️
Product level
PRODUCT.md (service map), DATAFLOW.md (event flows), INDEX.md (semantic router) generated across all services.
🤖
Serve
MCP server exposes tools: find_service, get_service_doc, search_index, get_dependencies. Works with Claude, Copilot, any MCP client.
What gets generated

12 documents per service, 3 product-level docs

Each document is audience-aware — written for both human engineers and AI agents.

OVERVIEW.md
Purpose, type, language, entry points, key abstractions
API.md
Every endpoint with method, auth, request/response, status codes, events
SCENARIOS.md
End-to-end flows with Mermaid sequence diagrams, function signatures, branch conditions, code snippets
BUSINESS_RULES.md
State machines, permission matrix, calculation formulas, business constraints
DATA_MODEL.md
DB entities, DTOs, validation rules, request/response objects
TABLE_MAP.md
Which tables this service owns vs reads, per-feature usage
DEPENDENCIES.md
Outbound calls, databases, third-party integrations with timeout/retry config
ARCHITECTURE.md
Layer diagram, module dependency graph, circular dependency detection
CONFIG.md
All env vars, feature flags, deployment notes
ERRORS.md
Error catalogue with HTTP status, retryability, recovery hints
CODING_STANDARDS.md
Architecture pattern, layer rules, naming conventions, anti-patterns
RUNBOOK.md
Health checks, startup/shutdown, failure modes, rollback steps, escalation
PRODUCT.md
Service map table + Mermaid dependency graph across all services
DATAFLOW.md
Event flows, data ownership, external integrations across the product
INDEX.md
Semantic router — agents start here to find the right service and document

PR-based automation

Keep the knowledge base in sync automatically

Run svcmap on every PR merge so docs stay fresh without manual effort. The knowledge base becomes a first-class CI artifact alongside your test reports.

1

PR opened

Developer opens a PR against a service. CI runs tests as normal.

2

PR merged to main

GitHub Action triggers on push to main. Detects which services changed using path filters.

3

svcmap regenerates affected services

Only changed services are re-crawled and re-generated. Unchanged services use cached docs.

4

Updated docs committed back

The action commits the updated Markdown files. Diff is reviewable in the PR timeline.

5

MCP server picks up changes

The running MCP server reads the updated docs on next query — no restart needed.

6

Agents answer immediately

Any AI assistant querying the MCP server gets the latest knowledge within minutes of the merge.

# .github/workflows/svcmap.yml name: Update knowledge base on: push: branches: [main] jobs: svcmap: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - name: Detect changed services id: changes uses: dorny/paths-filter@v3 with: filters: | payment: - 'src/paymentservice/**' checkout: - 'src/checkoutservice/**' - name: Regenerate payment docs if: steps.changes.outputs.payment == 'true' run: | node svcmap.js generate \ --service paymentservice env: ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }} GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }} - name: Commit updated docs run: | git config user.name "svcmap-bot" git add knowledge/ git diff --staged --quiet || \ git commit -m "docs: update knowledge base" git push

Use svcmap status in CI to check staleness without regenerating, and --save-extractions to cache raw JSON for debugging failed extractions.

Long-term value

Compound returns over time

Unlike a wiki that goes stale or a chatbot that hallucinates, svcmap docs are regenerated from source — they stay accurate and their value compounds with every query.

📈

Compounding query savings

Generation is a one-time cost. Every agent question answered from structured docs instead of raw source adds to the ROI. At 100 questions/day the payback is within days.

🧠

Organizational memory

Business rules, state machines, and runbook knowledge captured in structured docs survive team turnover. The next engineer doesn't need to find the person who wrote it.

🚀

Faster onboarding

New engineers understand the full product from INDEX.md and PRODUCT.md in one session. AI assistants can answer "how does the checkout flow work?" instantly with svcmap context.

🔗

Cross-team visibility

Other teams query your service via the MCP server without requiring access to your repo or a synchronous meeting. Dependency graphs and API contracts are always discoverable.

🛡️

Safer changes

TABLE_MAP.md and DEPENDENCIES.md make the blast radius of any change visible before it's made. Agents can answer "what breaks if I change this schema?" from structured data.

📜

Auditable history

Docs committed to git create a timeline of how each service evolved. The diff between two doc versions tells you what changed about the API contract or business rules — not just the code.

🔒

Privacy by design

Agents query a local MCP server, not GitHub directly. Raw source — including accidental secrets, API keys in comments, or PII in test fixtures — never reaches the LLM context window.

⚡

Sub-second agent responses

Pre-generated docs answer in <1 second from local disk. Without svcmap, agents spend 15–30 seconds crawling GitHub before they can answer, burning tokens and user patience.

🌐

Multi-agent ready

One knowledge base, one MCP server — serves Claude Desktop, VS Code Copilot, Cursor, and any other MCP-compatible agent simultaneously without redundant repo crawls.
