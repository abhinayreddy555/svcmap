# Data Model — spring-petclinic-visits-service

## TL;DR for Agents

- **1 core database entity** (`Visit`) and **1 primary DTO** — this is a minimal, focused microservice.
- The `Visit` entity records veterinary visits tied to a pet via `pet_id` (foreign key reference to the Pets service, **not** enforced at the DB level since this is a separate microservice).
- `pet_id` is the critical cross-service join key — it links visits to pets managed by `spring-petclinic-customers-service`.
- No enums are defined in this service.
- If your task involves visit records, appointment history, or pet-visit lookups, this document is relevant.

---

## Database Entities

### Visit

Represents a single veterinary visit (appointment) for a pet. Each visit captures the date and a textual description of the visit reason or outcome.

| Field | Type | Nullable | Index | FK → | Description |
|-------|------|----------|-------|------|-------------|
| `id` | `INTEGER` (auto-generated) | No | PK | — | Unique identifier for the visit record |
| `pet_id` | `INTEGER` | No | Yes (query index) | Logical → `customers-service.pets.id` | References the pet in the customers service |
| `visit_date` | `DATE` / `TIMESTAMP` | Yes | No | — | Date of the veterinary visit |
| `description` | `VARCHAR(255)` | Yes | No | — | Free-text description of the visit (reason, diagnosis, notes) |

**Relationships:**

- **Visit → Pet (logical, cross-service):** Each `Visit` references a `pet_id` that corresponds to a `Pet` entity managed by `spring-petclinic-customers-service`. Because these are separate microservices with separate databases, this is a **logical foreign key** — there is no physical FK constraint at the database level.
- A single pet can have **many** visits (one-to-many from Pet to Visit).

- **Visit.pet_id → Pet.id** (cross-service, logical): The visits service queries visits by `pet_id`. The customers service resolves pet details. No join is possible at the SQL level; correlation happens at the API gateway or aggregation layer.
- The primary query pattern is: **find all visits for a given pet** (`SELECT * FROM visits WHERE pet_id = ?`) or **find visits for a list of pets** (`SELECT * FROM visits WHERE pet_id IN (?)`).

## DTOs & Transfer Objects

### Visit `[domain-object]`

> In this microservice, the JPA entity itself is used as the transfer object in REST endpoints (no separate DTO class). The `Visit` entity is serialized/deserialized directly in request and response payloads.

**Used in:**
- `POST /owners/*/pets/{petId}/visits` — create a new visit for a pet
- `GET /owners/*/pets/{petId}/visits` — retrieve all visits for a pet
- `GET /pets/visits?petId={petId1}&petId={petId2}...` — retrieve visits for multiple pets (used by API gateway / composite endpoints)

| Field | Type | Required | Validation Rules | Description |
|-------|------|----------|------------------|-------------|
| `id` | `Integer` | No (auto-assigned on create) | — | Visit identifier; ignored on create requests |
| `petId` | `Integer` | Yes | Must reference a valid pet in customers-service | The pet this visit belongs to; set from path variable on create |
| `date` | `Date` (ISO 8601) | No | Should be a valid date; defaults may apply | Date of the visit |
| `description` | `String` | No | Max length 255 (column constraint) | Free-text visit description |

**Example request body (`POST`):**

```json
{
  "date": "2024-03-15",
  "description": "Annual vaccination"
}
```

> **Note:** `petId` is typically extracted from the URL path parameter rather than the request body. The `id` field is generated by the database.

**Example response body (`GET`):**

```json
[
  {
    "id": 1,
    "petId": 7,
    "date": "2024-03-15",
    "description": "Annual vaccination"
  }
]
```
